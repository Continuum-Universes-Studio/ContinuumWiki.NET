# CW-M5-023 — Administrative Recovery Authorization Provider and Activation Evidence

## Classification and boundary

`CATEGORY_ADMIN_AUTHORIZATION_SOURCE_VERIFIED`

This milestone is source-only. It made zero database connections and zero
database mutations. It did not reuse operator4 authority, activate a provider,
run recovery, change migrations, deploy services, enable routes, or modify Lua,
Cargo, workers, containers, or volumes.

Production migration and category/recovery repository activation remain
`NO_GO`.

## Existing security integration

The existing M5-022 controller remains protected by ASP.NET Core `[Authorize]`,
the hydrated `TwSessionState` administrator decision, anti-forgery attributes
on preview/execute, and the established page permission evaluator. The actor
passed to the recovery services is the server-derived profile user ID. No
request field can replace it.

Authentication and administrator membership are necessary but insufficient.
The API now consumes `ITwCategoryAdministrativeGrantProvider`, whose decision
is evaluated inside the existing recovery operation callback. Preview and
execute are evaluated independently; preview success is never an execute
grant. Page permission remains a separate callback and is re-evaluated by the
existing recovery services during execution.

## Typed grant contract

`TwCategoryAdministrativeGrant` contains:

- stable grant and approval IDs;
- approver identity and issuer evidence reference;
- server-bound actor identity;
- exact operation (`Preview` or `Execute`);
- normalized recovery scope and policy version;
- UTC issuance, not-before, and expiry times;
- revocation state; and
- reusable or single-use replay mode.

`TwCategoryAdministrativeGrantVerifier` rejects malformed IDs/evidence,
non-UTC or inverted intervals, not-yet-valid and expired grants, revoked
grants, actor/action/scope mismatches, and consumed grants. Scope comparison
uses the existing bounded fingerprint and policy version generated by
`TwCategoryRecoveryScope`; no client-supplied revision or database target is
accepted.

The default `TwCategoryAdministrativeGrantEvidenceSource` returns no grant,
and `TwCategoryAdministrativeGrantProvider` therefore returns a typed
`MissingGrant` denial. The old M5-022 authorization interface remains as a
compatibility subtype, but DI registers the typed provider path.

Single-use grants are denied unless the evidence source reports durable atomic
replay protection. The source implementation does not claim durable consume,
revocation, or concurrent single-use guarantees. Reusable grants are still
bounded by actor, action, scope, validity, and revocation evidence. A future
positive provider must perform atomic consume/revoke checks in its own
authorized durable store.

## Readiness evidence provenance

`ITwCategoryOperationalReadinessEvidenceSource.GetEvidence()` now carries
provenance, evidence ID, UTC observation/expiry, target binding, independent
source status, and a target-binding hash. The default source is explicitly
`SourceOnly` and never probes a database or provider.

Administrative execution accepts readiness evidence only when it is:

- independently sourced;
- target-bound;
- explicitly marked `ProductionDeployment`;
- identified by a nonempty evidence ID and binding hash; and
- within a valid UTC freshness window.

`DisposableCertification`, `OperatorReadinessProof`, and `SourceOnly` evidence
are rejected for production administrative execution. In particular, the
operator4 disposable certification cannot become production activation evidence
through DI reuse or a matching database identity.

The readiness evaluator remains pure and nonconnecting. The evidence policy is
an independent prerequisite; successful source evaluation or a healthy
provider alone cannot authorize mutation.

## API behavior and bounded outcomes

The existing routes remain:

| Route | Authorization behavior |
| --- | --- |
| `GET /Admin/CategoryRecovery/readiness` | authenticated administrator; returns redacted typed readiness only |
| `POST /Admin/CategoryRecovery/preview` | fresh preview grant, page permission, read-only `PlanAsync` |
| `POST /Admin/CategoryRecovery/execute` | fresh execute grant, production-bound readiness, page permission, durable recovery |

Missing, malformed, expired, revoked, replayed, mismatched, or unavailable
grant evidence is denied without reaching mutation. Readiness downgrade,
provider rejection, stale revision, incomplete expansion, inconsistent index,
cancellation, partial completion, persistence failure, and indeterminate
recovery remain typed outcomes. Unauthorized/disabled responses contain no
page names, revisions, membership counts, tokens, credentials, or raw payloads.

Existing batch ceiling 100, audit budget 4,096, authoritative revision
resolution, CAS, durable replay, cancellation, and recoverable two-phase
boundaries are unchanged. No direct SQL, retry worker, scheduler, lease,
cross-store transaction, or automatic activation was added.

provider rejection, anonymous/nonadmin access, grant validity and identity
binding, expiry/not-before/revocation, scope/action mismatch, single-use
replay protection limits, disposable-evidence rejection, preview-to-execute
non-escalation, page-permission revocation, batch limits, durable delegation,
partial/cancellation outcomes, redaction boundaries, and anti-forgery routes.

The full Debug and Release results are recorded in the companion machine report.
No live HTTP mutation endpoint was activated or invoked.

## Remaining independent gates

- A separately authorized durable grant/evidence provider is required before
  any real administrative preview or execution can be allowed.
- Durable atomic grant consume/revocation and concurrent replay prevention
  remain provider responsibilities and are not certified here.
- Production-bound readiness evidence and explicit production activation remain
  required; disposable MariaDB evidence is not transferable.
- No MariaDB, production, deployment, or host-worker certification was run.
